# Use Cases — Пользователи (User)

---

## UC-USER-01: Создать пользователя

**Актор:** `admin`  
**API:** `POST /api/v1/users/`

### Предусловия
- Текущий пользователь имеет роль `admin`
- `email` и `username` не заняты другим активным пользователем

### Порядок действий

1. Admin отправляет данные: `first_name`, `last_name`, `email`, `username`, `password`, `role`
2. Система проверяет роль текущего пользователя (`admin`); если нет — `403 Forbidden`
3. Система проверяет уникальность `email` в БД; если занят — `409 Conflict`
4. Система проверяет уникальность `username` в БД; если занят — `409 Conflict`
5. Валидирует `role` — должна быть одна из: `admin`, `director`, `sales_manager`, `consultant`
6. Хэширует `password` через Argon2
7. Создаёт запись `User` в БД со статусом `is_active = true`
8. Возвращает созданного пользователя (`201 Created`)

### Что решает
Единственная точка входа для регистрации сотрудников в системе. Только admin может добавлять участников — исключает самостоятельную регистрацию посторонних. Разграничение ролей с момента создания обеспечивает корректную изоляцию прав доступа.

### Альтернативные сценарии
- **Нет прав (не admin):** `403 Forbidden`
- **Email уже занят:** `409 Conflict`
- **Username уже занят:** `409 Conflict`
- **Невалидная роль:** `422 Unprocessable Entity`
- **Пароль не удовлетворяет требованиям:** `422`

### Постусловия
- Новый `User` создан в БД
- Пользователь может войти в систему через `UC-AUTH-01`

## UC-USER-02: Деактивировать пользователя

**Актор:** `admin`  
**API:** `PATCH /api/v1/users/{user_id}/deactivate` *(или через update)*

### Предусловия
- Текущий пользователь — `admin`
- Целевой пользователь существует и активен
- Admin не может деактивировать самого себя

### Порядок действий

1. Admin отправляет запрос на деактивацию с `user_id`
2. Система проверяет права `admin`; если нет — `403`
3. Система загружает пользователя по `user_id`; если не найден — `404`
4. Проверяет, что `user_id` != текущий `admin.id`; если совпадает — `400` («Нельзя деактивировать себя»)
5. Устанавливает `is_active = false`
6. Обновляет `updated_at`
7. Возвращает `200 OK`

### Что решает
Безопасное отключение уволенного или покинувшего компанию сотрудника без удаления исторических данных. Деактивированный пользователь теряет доступ к системе немедленно (при следующем запросе проверяется `is_active`), но его лиды и история остаются нетронутыми.

### Альтернативные сценарии
- **Пользователь не найден:** `404`
- **Попытка деактивировать себя:** `400`
- **Пользователь уже деактивирован:** `200 OK` (идемпотентно)

### Постусловия
- `User.is_active = false`
- Пользователь не может войти в систему

## UC-USER-03: Активировать пользователя

**Актор:** `admin`  
**API:** `PATCH /api/v1/users/{user_id}/activate` *(или через update)*

### Предусловия
- Текущий пользователь — `admin`
- Целевой пользователь существует и деактивирован

### Порядок действий

1. Admin отправляет запрос на активацию с `user_id`
2. Система проверяет права `admin`; если нет — `403`
3. Система загружает пользователя по `user_id`; если не найден — `404`
4. Устанавливает `is_active = true`
5. Обновляет `updated_at`
6. Возвращает `200 OK`

### Что решает
Восстановление доступа для пользователя (например, вернулся из отпуска или ошибочно деактивирован). Позволяет не создавать новый аккаунт и сохранить всю историю работы сотрудника.

### Альтернативные сценарии
- **Пользователь не найден:** `404`
- **Пользователь уже активен:** `200 OK` (идемпотентно)

### Постусловия
- `User.is_active = true`
- Пользователь может войти в систему
