## UC-ANALYTICS-01: Дашборд — сводные показатели

**Актор:** `admin`, `director`, `sales_manager`  
**API:** `GET /api/v1/analytics/dashboard`

### Предусловия
- Текущий пользователь имеет роль не ниже `sales_manager`
- Параметры: `date_from`, `date_to` (опциональны; по умолчанию — текущий месяц)

### Порядок действий

1. Система принимает параметры периода (`date_from`, `date_to`)
2. Применяет фильтр видимости по роли:
   - `admin`/`director` — все лиды
   - `sales_manager` — лиды своей команды
3. Выполняет агрегирующие запросы к таблице `leads`:

   **Всего лидов:** `COUNT(*) WHERE created_at BETWEEN date_from AND date_to AND is_deleted = false`

   **Конверсия (%):** `COUNT(*) WHERE closed_at IS NOT NULL AND stage.kind = 'won'` / `COUNT(*) всего * 100`

   **Открытые лиды по воронкам:** `COUNT(*) WHERE is_deleted = false AND stage.kind NOT IN ('won', 'lost')` GROUP BY `funnel_id`

   **Лиды по источникам (pie chart):** `COUNT(*) GROUP BY source.source_type`

4. Возвращает все виджеты в одном ответе

### Что решает
Даёт быстрый срез здоровья продаж: сколько заявок поступило, какой процент закрыт успешно, где скапливаются лиды. Позволяет руководителю оценить ситуацию одним взглядом на экран при открытии системы.

### Альтернативные сценарии
- **Нет прав (consultant):** `403`
- **Невалидный диапазон дат:** `422`
- **Нет данных за период:** возвращает нули

### Постусловия
- Состояние не изменяется (read-only)

## UC-ANALYTICS-02: Аналитика воронки (Funnel Analytics)

**Актор:** `admin`, `director`, `sales_manager`  
**API:** `GET /api/v1/analytics/funnel/{funnel_id}`

### Предусловия
- Воронка с `funnel_id` существует
- Параметры: `date_from`, `date_to`, `assign_to` (опциональны)

### Порядок действий

1. Система принимает параметры фильтрации
2. Загружает все этапы воронки, отсортированные по `order`
3. Для каждого этапа вычисляет:
   - `count` — текущее количество лидов на этапе (активных)
   - `total_entered` — сколько лидов когда-либо попало на этот этап за период (из `LeadHistory`)
4. Вычисляет конверсию между этапами: `(count[stage N+1] / count[stage N]) * 100`
5. Вычисляет среднее время нахождения лида на каждом этапе (из `LeadHistory`: разница между временем входа и выхода с этапа)
6. Применяет фильтры по `assign_to`, если указан
7. Возвращает данные для визуализации воронки

### Что решает
Показывает, где «застревают» лиды: если из 100 лидов на 1-м этапе до 2-го доходят только 20 — нужно разобраться, почему. Среднее время на этапе выявляет узкие места процесса. Визуализация воронки — классический инструмент управления продажами.

### Альтернативные сценарии
- **Воронка не найдена:** `404`
- **Нет прав:** `403`
- **Нет лидов в воронке:** конверсии = 0%

### Постусловия
- Состояние не изменяется (read-only)

## UC-ANALYTICS-03: Аналитика источников лидов

**Актор:** `admin`, `director`, `sales_manager`  
**API:** `GET /api/v1/analytics/sources`

### Предусловия
- Параметры: `date_from`, `date_to` (опциональны)

### Порядок действий

1. Система загружает все источники (`Source`)
2. Для каждого источника вычисляет за период:
   - `total` — количество лидов из этого источника
   - `won_count` — количество лидов, достигших этапа `won`
   - `conversion` — `won_count / total * 100`
3. Формирует данные динамики: количество новых лидов по источнику в разбивке по дням/неделям/месяцам (параметр `granularity`)
4. Возвращает таблицу и данные для графика

### Что решает
Позволяет определить самый эффективный канал привлечения: если webhook из одного сайта даёт 50% конверсию, а публичная форма — 5%, руководитель перераспределяет бюджет. ROI по каналам становится видимым без Excel.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Нет данных за период:** нули для всех источников

### Постусловия
- Состояние не изменяется (read-only)

## UC-ANALYTICS-04: Эффективность менеджеров

**Актор:** `admin`, `director`, `sales_manager`  
**API:** `GET /api/v1/analytics/managers`

### Предусловия
- Параметры: `date_from`, `date_to` (опциональны)
- Фильтр по роли:
  - `sales_manager` видит только свою команду
  - `admin`/`director` — всех

### Порядок действий

1. Система загружает список пользователей с ролями `sales_manager` и `consultant`
2. Для каждого пользователя вычисляет за период:
   - `total_leads` — лиды, где `assign_to = user.id`
   - `won_count` — из них достигли `won`
   - `lost_count` — из них достигли `lost`
   - `conversion` — `won_count / total_leads * 100`
   - `avg_close_time` — среднее время от создания лида до `closed_at` (только по `won`)
3. Сортирует по `conversion DESC` (или по выбору пользователя)
4. Возвращает таблицу менеджеров

### Что решает
Даёт объективные данные для оценки KPI команды: кто закрывает сделки быстро, кто теряет клиентов, у кого высокая нагрузка. Помогает руководителю принимать решения о перераспределении лидов, обучении или мотивации.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Менеджер без лидов:** строка отображается с нулями

### Постусловия
- Состояние не изменяется (read-only)

## UC-ANALYTICS-05: Динамика за период

**Актор:** `admin`, `director`, `sales_manager`  
**API:** `GET /api/v1/analytics/dynamics`

### Предусловия
- Параметры:
  - `period` — `yesterday` | `week` | `month` | `quarter` | `custom`
  - `date_from`, `date_to` — если `period = custom`
  - `granularity` — `day` | `week` | `month` (гранулярность точек на графике)

### Порядок действий

1. Система вычисляет диапазон дат на основе `period`
2. Генерирует временную шкалу с шагом `granularity`
3. Для каждой точки шкалы вычисляет:
   - `new_leads` — количество лидов, созданных за этот период (`created_at`)
   - `won_leads` — количество лидов, закрытых как `won` за этот период (`closed_at`, `stage.kind = 'won'`)
   - `lost_leads` — аналогично для `lost`
4. Применяет фильтр видимости по роли
5. Возвращает массив точек для построения графика

### Что решает
Показывает тренды: растёт ли бизнес, сезонность, влияние маркетинговых кампаний. Если в одну неделю количество новых лидов выросло в 3 раза — значит, сработала реклама. Если упало — нужно разобраться в причинах.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Невалидный диапазон дат:** `422`
- **`date_from > date_to`:** `422`
- **Нет данных за период:** массив точек с нулями (не пустой массив — сохраняется структура графика)

### Постусловия
- Состояние не изменяется (read-only)
