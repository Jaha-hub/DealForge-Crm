# Use Cases — Аутентификация (Auth)

---

## UC-AUTH-01: Вход в систему (Login)

**Актор:** Любой пользователь (anonymous)  
**API:** `POST /api/v1/auth/login`

### Предусловия
- Пользователь существует в системе
- Аккаунт активен (`is_active = true`)

### Порядок действий

1. Пользователь отправляет `username` и `password`
2. Система ищет пользователя по `username` в БД
3. Если пользователь не найден — возвращает `401 Unauthorized`
4. Система проверяет `is_active = true`; если нет — возвращает `403 Forbidden`
5. Система верифицирует пароль через Argon2 (сравнивает с `password_hash`)
6. Если пароль неверный — возвращает `401 Unauthorized`
7. Система генерирует **access token** (JWT, TTL 2 часа) и **refresh token** (JWT, TTL 7 дней)
8. Система обновляет поле `last_interaction` у пользователя
9. Возвращает оба токена клиенту

### Что решает
Идентифицирует пользователя и выдаёт JWT-пару для последующих запросов. Разделение на access/refresh позволяет минимизировать окно компрометации: короткоживущий access token используется в каждом запросе, долгоживущий refresh — только для обновления.

### Альтернативные сценарии
- **Пользователь не найден:** `401`, сообщение «Неверный логин или пароль»
- **Аккаунт деактивирован:** `403`, сообщение «Аккаунт заблокирован»
- **Неверный пароль:** `401`, сообщение «Неверный логин или пароль» (одинаковое с «не найден», чтобы не раскрывать существование аккаунта)

### Постусловия
- Клиент имеет валидную JWT-пару
- `User.last_interaction` обновлён

## UC-AUTH-02: Обновление токена (Refresh)

**Актор:** Любой аутентифицированный пользователь (anonymous с refresh token)  
**API:** `POST /api/v1/auth/refresh`

### Предусловия
- У клиента есть валидный, не истёкший refresh token

### Порядок действий

1. Клиент отправляет `refresh_token`
2. Система проверяет подпись и срок действия JWT
3. Если токен невалиден или истёк — возвращает `401`
4. Система извлекает `user_id` из payload токена
5. Система проверяет, что пользователь существует и активен
6. Генерирует новый **access token** (TTL 2 часа)
7. Возвращает новый access token клиенту

### Что решает
Позволяет клиенту получить новый access token без повторного ввода пароля. Обеспечивает бесперебойную работу сессии при истечении короткоживущего токена.

### Альтернативные сценарии
- **Невалидная подпись токена:** `401`
- **Токен истёк:** `401`, клиент перенаправляется на login
- **Пользователь деактивирован:** `403`

### Постусловия
- Клиент имеет новый валидный access token

## UC-AUTH-03: Получить профиль текущего пользователя (Get Me)

**Актор:** Любой аутентифицированный пользователь  
**API:** `GET /api/v1/auth/me`

### Предусловия
- Запрос содержит валидный access token в заголовке `Authorization: Bearer <token>`

### Порядок действий

1. Middleware извлекает и валидирует JWT из заголовка
2. Из payload извлекается `user_id`
3. Система загружает пользователя из БД по `user_id`
4. Если пользователь не найден или неактивен — `401`
5. Возвращает данные пользователя: `id`, `first_name`, `last_name`, `email`, `username`, `role`, `is_active`, `created_at`

### Что решает
Позволяет клиенту инициализировать интерфейс данными текущего пользователя (имя, роль, права) без повторного логина.

### Альтернативные сценарии
- **Токен отсутствует или невалиден:** `401`
- **Пользователь удалён из системы:** `401`

### Постусловия
- Состояние системы не изменяется (read-only)

## UC-AUTH-04: Обновить профиль (Update Me)

**Актор:** Любой аутентифицированный пользователь  
**API:** `PATCH /api/v1/auth/me`

### Предусловия
- Пользователь аутентифицирован

### Порядок действий

1. Клиент отправляет поля для обновления: `first_name`, `last_name` (оба опциональны)
2. Система валидирует входные данные (длина, тип)
3. Система обновляет указанные поля пользователя
4. Обновляет `updated_at`
5. Возвращает обновлённый профиль

### Что решает
Позволяет пользователю поддерживать актуальность своих данных в системе.

### Альтернативные сценарии
- **Пустой body:** поля остаются прежними, `200 OK`
- **Невалидное значение (слишком длинное имя):** `422 Unprocessable Entity`

### Постусловия
- `User.first_name` и/или `User.last_name` обновлены
- `User.updated_at` обновлён

## UC-AUTH-05: Смена пароля (Change Password)

**Актор:** Любой аутентифицированный пользователь  
**API:** `POST /api/v1/auth/change-password`

### Предусловия
- Пользователь аутентифицирован

### Порядок действий

1. Клиент отправляет `old_password` и `new_password`
2. Система загружает текущего пользователя
3. Верифицирует `old_password` через Argon2
4. Если старый пароль не совпадает — `400 Bad Request`
5. Валидирует `new_password` (минимальная длина, требования к сложности)
6. Хэширует новый пароль через Argon2
7. Обновляет `User.password_hash`
8. Обновляет `updated_at`
9. Возвращает `200 OK`

### Что решает
Позволяет пользователю самостоятельно сменить пароль, не требуя участия администратора. Защищает аккаунт при компрометации: проверка старого пароля исключает несанкционированную смену.

### Альтернативные сценарии
- **Старый пароль неверный:** `400`, сообщение «Неверный текущий пароль»
- **Новый пароль слишком короткий:** `422`
- **Новый пароль совпадает со старым:** опционально `400` (business decision)

### Постусловия
- `User.password_hash` обновлён
- Существующие токены не инвалидируются (stateless JWT — токены истекают по TTL)
