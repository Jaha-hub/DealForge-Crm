# Use Cases — Лиды (Lead)

## UC-LEAD-01: Создать лид вручную

**Актор:** `sales_manager`, `director`, `admin`; `consultant` — в любой воронке  
**API:** `POST /api/v1/leads/`

### Предусловия
- Пользователь аутентифицирован
- Воронка (`funnel_id`) и этап (`stage_id`) существуют и активны
- `stage_id` принадлежит `funnel_id`
- Источник (`source_id`) существует и типа `manual`

### Порядок действий

1. Пользователь отправляет: `name`, `phone`/`email`, `source_id`, `funnel_id`, `stage_id`, опционально `comment`, `tags`, `assign_to`
2. Система проверяет аутентификацию
3. Проверяет, что роль не ниже `consultant` (все роли могут создавать лид)
4. Валидирует `name` (2–255 символов)
5. Проверяет, что хотя бы одно из `phone`/`email` заполнено (value object `Contact`)
6. Проверяет существование `funnel_id`; если не найдена — `404`
7. Проверяет существование `stage_id` и его принадлежность `funnel_id`; если нет — `422`
8. Проверяет существование `source_id`; если не найден — `404`
9. Если `assign_to` указан — проверяет существование пользователя
10. Создаёт `Lead` со всеми полями, `is_deleted = false`, `closed_at = null`
11. Записывает `LeadHistory` (action `created`, `user_id = текущий пользователь`)
12. Если `assign_to` указан — создаёт уведомление назначенному (event_type `lead_assigned`)
13. Возвращает созданный лид (`201 Created`)

### Что решает
Позволяет менеджеру вручную завести лид после телефонного звонка, встречи или другого офлайн-контакта. Явная привязка к воронке и этапу гарантирует корректное отображение на Kanban-доске сразу после создания.

### Альтернативные сценарии
- **Нет `phone` и `email`:** `422` — «Укажите хотя бы один контакт»
- **`stage_id` не принадлежит воронке:** `422`
- **`assign_to` не найден:** `404`
- **Воронка удалена:** `404`

### Постусловия
- `Lead` создан в БД
- `LeadHistory` содержит запись `created`
- Если назначен — уведомление `lead_assigned` отправлено

## UC-LEAD-02: Получить лид

**Актор:** Аутентифицированный пользователь (с учётом правил видимости)  
**API:** `GET /api/v1/leads/{lead_id}`

### Предусловия
- Лид существует, не удалён
- Текущий пользователь имеет право видеть лид (см. правила ниже)

### Правила видимости
| Роль | Видит |
|---|---|
| `admin`, `director` | Все лиды |
| `sales_manager` | Лиды своей команды (лиды, где `assign_to` — его подчинённый) |
| `consultant` | Только лиды, где `assign_to = текущий пользователь` |

### Порядок действий

1. Система загружает лид по `lead_id`
2. Если не найден или `is_deleted = true` — `404`
3. Применяет фильтр видимости по роли текущего пользователя
4. Если нет доступа — `403 Forbidden`
5. Загружает связанные данные: источник, воронку, этап, ответственного, кастомные значения
6. Возвращает полную карточку лида

### Что решает
Предоставляет полные данные лида для отображения карточки. Фильтр видимости обеспечивает изоляцию: `consultant` физически не может увидеть чужой лид, даже зная его ID.

### Альтернативные сценарии
- **Лид не найден:** `404`
- **Нет прав доступа к этому лиду:** `403`

### Постусловия
- Состояние не изменяется (read-only)

## UC-LEAD-03: Список лидов

**Актор:** Аутентифицированный пользователь  
**API:** `GET /api/v1/leads/`

### Предусловия
- Пользователь аутентифицирован

### Порядок действий

1. Система принимает опциональные параметры фильтрации: `funnel_id`, `stage_id`, `source_id`, `assign_to`, `tags[]`, `created_from`, `created_to`, `is_deleted`
2. Применяет базовый фильтр видимости по роли (те же правила, что в `UC-LEAD-02`)
3. Применяет переданные фильтры поверх
4. Сортирует по `created_at DESC` (по умолчанию)
5. Поддерживает пагинацию (`offset` / `limit` или курсорная)
6. Возвращает список лидов с базовыми полями (без кастомных значений — для производительности)

### Что решает
Основной endpoint для Kanban-доски (фильтр по `funnel_id`) и списочного представления. Многоуровневая фильтрация позволяет менеджеру быстро найти нужные лиды без лишних запросов.

### Альтернативные сценарии
- **Нет лидов, подходящих под фильтр:** `[]` с `200 OK`
- **Невалидный параметр фильтра:** `422`

### Постусловия
- Состояние не изменяется (read-only)

## UC-LEAD-04: Обновить поля лида

**Актор:** Назначенный пользователь (`assign_to`), `sales_manager`, `director`, `admin`  
**API:** `PUT /api/v1/leads/{lead_id}`

### Предусловия
- Лид существует и не удалён
- Текущий пользователь имеет право редактировать лид

### Порядок действий

1. Пользователь отправляет обновляемые поля: `name`, `phone`, `email`, `comment`, `tags`
2. Система проверяет доступ к лиду (видимость + право редактирования)
3. Если нет прав — `403`
4. Загружает лид; если не найден — `404`
5. Для каждого изменённого поля: сохраняет старое значение (`old_value`) и новое (`new_value`)
6. Валидирует обновляемые поля (длина `name`, формат контактов)
7. Применяет изменения
8. Обновляет `updated_at`
9. Для каждого изменённого поля записывает `LeadHistory` (action `field_updated`)
10. Возвращает обновлённый лид

### Что решает
Позволяет актуализировать контактные данные лида и добавлять заметки по ходу работы. История изменений (LeadHistory) обеспечивает аудит: руководитель всегда видит, кто и когда изменил данные.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Лид не найден:** `404`
- **Попытка убрать оба контакта (`phone` = null, `email` = null):** `422`
- **Невалидный `name`:** `422`

### Постусловия
- Поля `Lead` обновлены
- `LeadHistory` содержит записи `field_updated` для каждого изменённого поля
- `Lead.updated_at` обновлён

## UC-LEAD-05: Перевести лид на другой этап

**Актор:** Назначенный пользователь, `sales_manager`, `director`, `admin`  
**API:** `PATCH /api/v1/leads/{lead_id}/stage`

### Предусловия
- Лид существует и не удалён
- Новый `stage_id` существует и принадлежит той же воронке, что и лид
- Текущий пользователь имеет доступ к лиду

### Порядок действий

1. Пользователь отправляет `stage_id` (новый этап)
2. Система проверяет доступ; если нет — `403`
3. Загружает лид; если не найден — `404`
4. Загружает новый `FunnelStage`; если не найден — `404`
5. Проверяет, что `FunnelStage.funnel_id == Lead.funnel_id`; если нет — `422`
6. Сохраняет `old_stage_id = Lead.stage_id`
7. Обновляет `Lead.stage_id = новый stage_id`
8. **Если новый этап `kind = won` или `kind = lost`:**
   - Устанавливает `Lead.closed_at = now()`
9. **Если новый этап `kind = initial` или `kind = intermediate` (возврат из won/lost):**
   - Обнуляет `Lead.closed_at = null`
10. Обновляет `Lead.updated_at`
11. Записывает `LeadHistory` (action `stage_changed`, `old_value = {stage_id: old}`, `new_value = {stage_id: new}`)
12. Если назначен пользователь — создаёт уведомление (event_type `stage_changed`)
13. Если возврат из `won`/`lost` → `intermediate` — создаёт уведомление `sales_manager` (event_type `lead_restored`)
14. Возвращает обновлённый лид

### Что решает
Ключевое бизнес-действие — продвижение лида по воронке. Автоматическое проставление `closed_at` при попадании на `won`/`lost` обеспечивает корректную аналитику времени закрытия сделки. Возврат из закрытых этапов обнуляет дату — лид снова «открыт».

### Альтернативные сценарии
- **Нет прав:** `403`
- **Лид удалён:** `404`
- **`stage_id` принадлежит другой воронке:** `422`
- **Этап не существует:** `404`

### Постусловия
- `Lead.stage_id` обновлён
- `Lead.closed_at` установлен (если `won`/`lost`) или сброшен (если возврат)
- `LeadHistory` содержит запись `stage_changed`
- Уведомления отправлены

## UC-LEAD-06: Назначить менеджера

**Актор:** `sales_manager`, `director`, `admin`  
**API:** `PATCH /api/v1/leads/{lead_id}/assign`

### Предусловия
- Лид существует и не удалён
- Назначаемый пользователь существует и активен
- Текущий пользователь имеет право назначать (`sales_manager`, `director`, `admin`)

### Порядок действий

1. Пользователь отправляет `assign_to` (UUID пользователя) или `null` (снять назначение)
2. Система проверяет роль; если `consultant` — `403`
3. Загружает лид; если не найден — `404`
4. Если `assign_to` != null — загружает назначаемого пользователя; если не найден — `404`
5. Сохраняет `old_assign_to = Lead.assign_to`
6. Обновляет `Lead.assign_to = новый пользователь`
7. Обновляет `updated_at`
8. Записывает `LeadHistory` (action `assigned`)
9. Если назначен новый пользователь — создаёт уведомление ему (event_type `lead_assigned`)
10. Возвращает обновлённый лид

### Что решает
Управление ответственностью за лид. Менеджер назначает конкретного консультанта — после этого тот видит лид в своём списке и получает уведомление. Снятие назначения (`assign_to = null`) возвращает лид в «неназначенный» пул.

### Альтернативные сценарии
- **`consultant` пытается назначить:** `403`
- **Лид не найден:** `404`
- **Назначаемый пользователь не найден:** `404`
- **Назначение на себя:** разрешено

### Постусловия
- `Lead.assign_to` обновлён
- `LeadHistory` содержит запись `assigned`
- Уведомление `lead_assigned` отправлено новому ответственному

## UC-LEAD-07: Удалить лид (Soft Delete)

**Актор:** `director`, `admin`  
**API:** `DELETE /api/v1/leads/{lead_id}`

### Предусловия
- Текущий пользователь — `director` или `admin`
- Лид существует и не удалён

### Порядок действий

1. Система проверяет роль; если нет — `403`
2. Загружает лид; если не найден — `404`
3. Устанавливает `Lead.is_deleted = true`
4. Обновляет `updated_at`
5. Записывает `LeadHistory` (action `deleted`)
6. Возвращает `204 No Content`

### Что решает
Убирает некачественный или дублирующийся лид из активной работы без потери данных. Soft delete гарантирует, что история и аналитика за предыдущие периоды остаются корректными.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Лид не найден:** `404`
- **Лид уже удалён:** `404`

### Постусловия
- `Lead.is_deleted = true`
- Лид не отображается в списке активных
- `LeadHistory` содержит запись `deleted`

## UC-LEAD-08: Восстановить лид

**Актор:** `admin`  
**API:** `PATCH /api/v1/leads/{lead_id}/restore` *(подразумевается)*

### Предусловия
- Текущий пользователь — `admin`
- Лид существует и удалён (`is_deleted = true`)

### Порядок действий

1. Система проверяет роль (`admin`); если нет — `403`
2. Загружает лид (включая удалённые); если не найден — `404`
3. Проверяет, что `is_deleted = true`; если нет — `400` («Лид не удалён»)
4. Устанавливает `Lead.is_deleted = false`
5. Обновляет `updated_at`
6. Записывает `LeadHistory` (action `restored`)
7. Возвращает восстановленный лид

### Что решает
Позволяет откатить случайное удаление. Только `admin` имеет эту привилегию — предотвращает злоупотребление восстановлением.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Лид не найден:** `404`
- **Лид не удалён:** `400`

### Постусловия
- `Lead.is_deleted = false`
- `LeadHistory` содержит запись `restored`
- Лид снова отображается в списке активных

## UC-LEAD-09: История изменений лида

**Актор:** Аутентифицированный пользователь (с доступом к лиду)  
**API:** `GET /api/v1/leads/{lead_id}/history`

### Предусловия
- Лид существует (в том числе если удалён — история доступна)
- Текущий пользователь имеет доступ к лиду (те же правила видимости)

### Порядок действий

1. Система проверяет доступ к лиду; если нет — `403`
2. Загружает все записи `LeadHistory` для данного `lead_id`
3. Сортирует по `created_at DESC` (новые события — сверху)
4. Возвращает список: `action`, `old_value`, `new_value`, `user_id`, `created_at` (+ имя пользователя, если `user_id != null`)

### Что решает
Предоставляет полный аудит-трейл для карточки лида. Менеджер видит хронологию событий: кто создал, кто изменил данные, кто перевёл на этап. Системные события (webhook) видны с `user_id = null`.

### Альтернативные сценарии
- **Нет доступа к лиду:** `403`
- **Лид не найден:** `404`
- **История пуста:** `[]` (теоретически невозможно — `created` всегда есть)

### Постусловия
- Состояние не изменяется (read-only)
