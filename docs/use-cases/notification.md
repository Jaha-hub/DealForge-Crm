# Use Cases — Уведомления (Notification)

---

## UC-NOTIF-01: Получить список уведомлений

**Актор:** Любой аутентифицированный пользователь  
**API:** `GET /api/v1/notifications/`

### Предусловия
- Пользователь аутентифицирован

### Порядок действий

1. Система определяет `user_id` текущего пользователя из JWT
2. Загружает все уведомления, где `Notification.user_id = текущий user_id`
3. По умолчанию фильтрует только непрочитанные (`is_read = false`); с параметром `?all=true` — возвращает все
4. Сортирует по `created_at DESC` (новые — сверху)
5. Возвращает список уведомлений и счётчик непрочитанных (`unread_count`)

### Что решает
Предоставляет данные для ленты уведомлений в хедере платформы. При открытии уведомлений пользователь видит, что произошло с его лидами пока он отсутствовал.

### Альтернативные сценарии
- **Нет уведомлений:** `[]`, `unread_count = 0`

### Постусловия
- Состояние не изменяется (read-only)

## UC-NOTIF-02: Отметить уведомление прочитанным

**Актор:** Любой аутентифицированный пользователь  
**API:** `PATCH /api/v1/notifications/{id}/read`

### Предусловия
- Уведомление с `id` существует
- Уведомление принадлежит текущему пользователю

### Порядок действий

1. Система определяет `user_id` из JWT
2. Загружает уведомление по `id`; если не найдено — `404`
3. Проверяет, что `Notification.user_id == текущий user_id`; если нет — `403`
4. Устанавливает `is_read = true`
5. Возвращает `200 OK`

### Что решает
Позволяет пользователю явно подтвердить, что он ознакомился с уведомлением. После отметки счётчик непрочитанных в хедере уменьшается. Уведомление не удаляется — остаётся в ленте для последующего просмотра.

### Альтернативные сценарии
- **Уведомление не найдено:** `404`
- **Уведомление принадлежит другому пользователю:** `403`
- **Уведомление уже прочитано:** `200 OK` (идемпотентно)

### Постусловия
- `Notification.is_read = true`

## UC-NOTIF-03: Отметить все уведомления прочитанными

**Актор:** Любой аутентифицированный пользователь  
**API:** `PATCH /api/v1/notifications/read-all`

### Предусловия
- Пользователь аутентифицирован

### Порядок действий

1. Система определяет `user_id` из JWT
2. Выполняет bulk UPDATE: `is_read = true` для всех записей, где `user_id = текущий user_id` и `is_read = false`
3. Возвращает `200 OK` с количеством обновлённых записей (опционально)

### Что решает
Быстрое «очистить всё» — пользователь сбрасывает счётчик одним кликом. Удобно после длительного отсутствия, когда накопилось много уведомлений.

### Альтернативные сценарии
- **Нет непрочитанных:** `200 OK`, `updated = 0`

### Постусловия
- Все `Notification.is_read = true` для данного пользователя
- `unread_count = 0`

## UC-NOTIF-04: WebSocket — подключение и получение уведомлений в реальном времени

**Актор:** Любой аутентифицированный пользователь  
**API:** `WS /ws/notifications`

### Предусловия
- Клиент имеет валидный JWT-токен (передаётся в query-параметре или заголовке при handshake)

### Порядок действий

#### При подключении (handshake)

1. Клиент открывает WebSocket-соединение: `ws://host/ws/notifications?token=<jwt>`
2. Сервер валидирует JWT; если токен невалиден — закрывает соединение с кодом `4001 Unauthorized`
3. Сервер регистрирует соединение в списке активных соединений для `user_id`
4. Сервер отправляет начальное сообщение:
   ```json
   {
     "type": "init",
     "unread_count": 3,
     "notifications": [/* список непрочитанных */]
   }
   ```

#### При создании нового уведомления в системе

1. Какое-либо действие (назначение лида, смена этапа и т.д.) создаёт `Notification` в БД
2. Сервер определяет `user_id` получателя
3. Ищет активное WebSocket-соединение для этого `user_id`
4. Если соединение активно — отправляет push-сообщение:
   ```json
   {
     "type": "notification",
     "id": "uuid",
     "title": "Новый лид назначен",
     "body": "Лид «Иван Иванов» назначен на вас",
     "event_type": "lead_assigned",
     "payload": { "lead_id": "uuid" },
     "created_at": "2026-05-14T10:00:00Z"
   }
   ```
5. Если соединения нет — уведомление сохранено в БД и будет получено при следующем подключении через `UC-NOTIF-01`

#### При отключении

1. Клиент закрывает вкладку/браузер
2. Сервер удаляет соединение из списка активных
3. Новые уведомления для этого `user_id` накапливаются в БД

### Что решает
Мгновенная доставка событий без polling. Пользователь видит значок нового уведомления в хедере в тот же момент, когда произошло событие (назначили лид, перевели на этап). Это критично для оперативной реакции команды продаж. Дублирование в БД гарантирует, что оффлайн-пользователь не пропустит уведомление.

### Альтернативные сценарии
- **Невалидный JWT при подключении:** WS-соединение закрывается с кодом `4001`
- **Истёк JWT во время сессии:** сервер закрывает соединение, клиент перезапрашивает токен через refresh
- **Пользователь открыл несколько вкладок:** каждая вкладка — отдельное WS-соединение, сервер рассылает всем

### Постусловия
- Пользователь получает уведомления в реальном времени без перезагрузки страницы
