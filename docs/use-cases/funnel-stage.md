# Use Cases — Этапы воронки (FunnelStage)

---

## UC-STAGE-01: Создать этап воронки

**Актор:** `admin`, `director`  
**API:** `POST /api/v1/funnels/{funnel_id}/stages/`

### Предусловия
- Текущий пользователь — `admin` или `director`
- Воронка с `funnel_id` существует и не удалена
- Порядок (`order`) уникален в пределах данной воронки

### Порядок действий

1. Пользователь отправляет: `name`, `win_probability` (0–100), `hex` (цвет), `order`, `kind`
2. Система проверяет роль; если нет — `403`
3. Загружает воронку по `funnel_id`; если не найдена — `404`
4. Валидирует `win_probability` (целое число 0–100)
5. Валидирует `hex` (формат `#RRGGBB`)
6. Валидирует `kind` (одно из: `initial`, `intermediate`, `won`, `lost`)
7. Проверяет уникальность `order` в пределах воронки; если занят — `409`
8. Создаёт `FunnelStage` с `is_archived = false`
9. Возвращает созданный этап (`201 Created`)

### Что решает
Позволяет гибко настраивать шаги воронки под конкретный бизнес-процесс. Параметр `win_probability` даёт прогноз вероятности успеха на каждом этапе. Параметр `order` управляет порядком колонок в Kanban-доске. Тип (`kind`) определяет специальное поведение: `won`/`lost` автоматически закрывают сделку, `initial` — принимает лиды от webhook/формы.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Воронка не найдена:** `404`
- **Дублирующийся `order`:** `409 Conflict`
- **Невалидный `hex`:** `422`
- **`win_probability` вне диапазона 0–100:** `422`
- **Невалидный `kind`:** `422`

### Постусловия
- Новый `FunnelStage` создан и привязан к воронке
- Если `kind = initial` — этот этап становится целевым для webhook и публичной формы данной воронки

## UC-STAGE-02: Список этапов воронки

**Актор:** Любой аутентифицированный пользователь  
**API:** `GET /api/v1/funnels/{funnel_id}/stages`

### Предусловия
- Воронка с `funnel_id` существует

### Порядок действий

1. Система загружает все этапы воронки (`funnel_id = funnel_id`)
2. Фильтрует по `is_archived = false` (по умолчанию) либо возвращает все (если передан параметр `include_archived=true`)
3. Сортирует по полю `order` (по возрастанию)
4. Возвращает список этапов

### Что решает
Предоставляет упорядоченный список колонок для Kanban-доски и данные о вероятности выигрыша для аналитики.

### Альтернативные сценарии
- **Воронка не найдена:** `404`
- **Нет этапов:** возвращает `[]`

### Постусловия
- Состояние системы не изменяется (read-only)

## UC-STAGE-03: Обновить этап воронки

**Актор:** `admin`, `director`  
**API:** `PUT /api/v1/funnels/{funnel_id}/stages/{stage_id}`

### Предусловия
- Текущий пользователь — `admin` или `director`
- Этап существует и принадлежит указанной воронке
- Если меняется `order` — новый порядок уникален в воронке

### Порядок действий

1. Пользователь отправляет обновляемые поля: `name`, `win_probability`, `hex`, `order`, `kind`, `is_archived`
2. Система проверяет роль; если нет — `403`
3. Загружает этап по `stage_id` и `funnel_id`; если не найден — `404`
4. Валидирует каждое обновляемое поле
5. Если меняется `order` — проверяет уникальность нового `order` в воронке
6. Применяет изменения
7. Обновляет `updated_at`
8. Возвращает обновлённый этап

### Что решает
Позволяет переименовывать этапы, менять их порядок на Kanban-доске, корректировать вероятность выигрыша и цвет. Архивирование (`is_archived = true`) скрывает этап из Kanban, не затрагивая лидов, которые на нём находятся.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Этап не найден:** `404`
- **Конфликт порядка:** `409`
- **Невалидные данные:** `422`

### Постусловия
- Поля `FunnelStage` обновлены
- Если `is_archived = true` — этап исчезает из Kanban-доски, лиды остаются

## UC-STAGE-04: Удалить этап воронки

**Актор:** `admin`  
**API:** `DELETE /api/v1/funnels/{funnel_id}/stages/{stage_id}`

### Предусловия
- Текущий пользователь — `admin`
- Этап существует и принадлежит воронке
- На этапе **нет** активных лидов (или система запрещает удаление при наличии лидов)
- Нельзя удалить последний `initial` этап в воронке

### Порядок действий

1. Система проверяет роль; если нет — `403`
2. Загружает этап; если не найден — `404`
3. Проверяет наличие лидов на этапе; если есть — `409 Conflict` («На этапе есть лиды, переместите их перед удалением»)
4. Проверяет, что воронка не лишится последнего `initial` этапа; если это последний — `400`
5. Удаляет этап из БД (физическое удаление; каскадом при удалении воронки)
6. Возвращает `204 No Content`

### Что решает
Позволяет избавиться от ненужных этапов без потери данных (нет лидов — нет риска). Защита от удаления `initial` этапа гарантирует, что webhook и форма всегда смогут создать лид в воронке.

### Альтернативные сценарии
- **Нет прав:** `403`
- **Этап не найден:** `404`
- **На этапе есть лиды:** `409`
- **Последний `initial` этап:** `400`

### Постусловия
- `FunnelStage` физически удалён из БД
